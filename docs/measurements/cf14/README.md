# CF-14: MySQL adapter measurement, stage 1

This is an exploratory synthetic measurement of the production MySQL adapter at
`a5e22c7a1e6c89c091d0e3ef267c17dddaaa208d`. It is not a TUI benchmark, a DB benchmark,
a GCP acceptance result, or a completed CF-14 optimization decision. No production
performance code changes are included. CF-13 remains deferred; cloud environments
and the aggregate branch's merge into main are outside this work.

## Reproduce

Use a Unix host with Python 3 and the repository Rust toolchain. No mysql client,
DB, Docker, or credentials are needed. The Rust executable calls the real
`MySqlAdapter` ports; the Python executable named `mysql` supplies synthetic XML.
The runner prepends this directory to PATH. The hardcoded DSN selects an invented
`fixture` user and `app` database at loopback port 1; the fake ignores the option
file and never connects to that address. Do not replace the fake with a real CLI.

```sh
RUSTC_WRAPPER= CARGO_TARGET_DIR=/tmp/sabiql-cf14-target cargo build -p sabiql-infra --example cf14_mysql
python3 scripts/cf14/run.py --binary /tmp/sabiql-cf14-target/debug/examples/cf14_mysql --output /tmp/cf14-new-run
python3 scripts/cf14/faults.py --binary /tmp/sabiql-cf14-target/debug/examples/cf14_mysql --output /tmp/cf14-new-faults
```

Output directories must not exist. Keep the result directory as an artifact;
`cargo clean --target-dir /tmp/sabiql-cf14-target` removes only build products.
`--smoke` runs all selected operations at 0 ms/10 tables with one pair.
`--operations db_selection` restricts a repeat to that operation.
The loopback fixture requires permission to bind a local ephemeral port.

## Protocol and boundaries

The matrix is response delay 0/50/200 ms × 10/100/1000 tables × five ordered pairs.
Order is delay, table count, operation in the manifest, then repetition 0–4.
Each fresh process performs the same operation twice: `fresh-harness`, then
`repeated-harness`. This does not flush OS caches or populate an application/DB
cache. The stateless adapter still starts new fake CLI processes for each call.
Timing excludes Rust executable startup but includes Python process startup,
option-file I/O, XML parsing, and adapter cleanup. Development-profile builds and
ordinary host scheduling were used; this is not a controlled machine comparison.

A single sleep is injected immediately before each nonempty XML response, after
building its contents. SET statements return no XML and have no injected delay.
This is **synthetic response delay, not RTT**; there is no normal-case socket or
DB handshake, and no simulated bandwidth limit. Tables have one integer primary
key, 100 estimated rows, no secondary indexes/FKs/triggers, and 50 returned preview
rows. Catalog size changes the listed/signature tables; a selected table stays
one table. It does not simulate a complex real schema.

| Operation | Measured adapter boundary |
|---|---|
| startup | CLI version check and server probe, not TUI/process startup |
| db_selection | probe → metadata → effective user; ends after user retrieval, not list display |
| metadata_reload | metadata port only; no downstream reducer effects |
| table_selection | concurrent detail and preview ports, ends when both return |
| inspector | full detail for `app.items` |
| preview / page | 50 rows, offsets 0 / 50 |
| completion | columns/FKs for one selected table, not whole editor completion latency |
| er_metadata | schema signatures and prefetched details, not Graphviz/file/viewer |

The DB ordering follows `connection/helpers.rs::mysql_connection_completion_effects`
and `browse/metadata/loading.rs::MetadataLoaded`; no reducer, event loop, drawing,
debounce, cache restoration, or live UI is driven by this harness.

Each pair's JSONL contains fake process start/exit timestamps and observed SQL
text, with generated marker values replaced by `<marker>`. Each event opens,
writes and closes the log before returning: its Python buffer is flushed before
the fake emits the corresponding XML. A successful validated response therefore
follows its SQL event; malformed/truncated log JSON makes collection fail. The
exit event is different: SIGKILL can prevent it entirely. XML byte events precede
the delay and stdout write, so they record generated bytes even for a fault whose
response is never delivered. They are not received-byte telemetry. Samples include the
original wall-clock interval and monotonic elapsed milliseconds. Clock timestamps
associate events with operations, so wall-clock adjustments invalidate that
association. SQL text bytes count stripped SQL UTF-8, excluding delimiters and
transport framing; XML bytes count generated response UTF-8, not measured network
transfer or all CLI stdout. Version output bytes are excluded. Process totals
include the version-check process; maximum concurrency is unmeasured. The adapter may kill a successful fake before
its Python exit handler runs, so start-minus-exit counters overestimate overlap.
That initial derived counter was invalidated to null; the underlying raw events
were preserved. The earlier smoke claim of maximum concurrency two is withdrawn. Residual PIDs are checked with `kill(pid, 0)`
after both calls return, not continuously or at the exact cancellation instant.

Real DB connections, RTT, rendering, application-cache behavior, network bytes,
DB-side cancel/rollback and SQL execution times remain unmeasured. Null fields
mean unmeasured, never zero. The normal-case fake opens no DB connection, which
does not establish how many a real CLI would open. No SQL-count-to-RTT inference
is used. Summary p95 uses nearest rank: with five samples it is the maximum.
Raw times and min/max are retained; these tails are descriptive, not stable p95
estimates. Each matrix run has a 20-minute/20-MiB budget checked between pairs,
and an 80-second per-pair watchdog. The matrix is intentionally small.

## Retained runs

- `baseline-a5e22c7a`: initial nine-operation sweep. **Exclude every db_selection
  sample and summary from comparisons**: its initial implementation ran metadata
  and user concurrently, and was corrected during the sweep. These exploratory
  values are retained rather than erased.
  All other operation boundaries were unchanged.
- `db-selection-a5e22c7a`: separate, corrected sequential DB selection sweep.
  This is the authoritative DB selection adapter measurement. Its endpoint is
  user completion; metadata/list readiness and drawing were not timed separately.
- `loopback-a5e22c7a`: two calls per fault, 10 tables, no synthetic response delay.
  A dedicated Python TCP listener accepts only the fake CLI's local connection.
  It closes immediately, or holds the first nonempty XML response until adapter
  timeout/cancellation. Loopback accepts are real observations of this fixture,
  **not DB connection counts**. Probe timeout and metadata timeout retain their
  distinct adapter stages. Cancel aborts and joins a Rust task after 250 ms;
  it does not exercise the application's cancel action. Residual PIDs are checked
  500 ms after the two calls. Peer EOF events are retained. No DB rollback claim.

CSV was not run: the public export port chooses the user's Downloads/home path.
A future measurement can use a test-only, caller-owned output path at the existing
CSV writer boundary: an ignored measurement test inside the MySQL CLI module can
call `export_mysql_csv_to_file` with a `TempDir` path, without a new public API or
changes to production export behavior. PostgreSQL,
actual cold/warm DB/cache, full startup/reload/completion/ER/CSV workflows, TUI
list/Inspector/preview readiness, refusal-before-connect, and DB-side cancellation
remain follow-up work. CF-02/07 post-merge comparison must use separately named
runs on the new base; these baseline values must not be relabeled as post-change.
