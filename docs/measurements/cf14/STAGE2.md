# CF-14 stage 2: CSV and connection-cache boundaries

Production code is unchanged. These measurements use the real MySQL adapter and
synthetic CLI XML responses. No database, Auth Proxy or cloud is used. This stage
does not complete CF-14, validate cloud support, or establish a performance change.
CF-13 remains deferred.

## Reproduction and bounds

```sh
RUSTC_WRAPPER= CARGO_TARGET_DIR=/private/tmp/cf14-stage2-target \
  cargo test -p sabiql --bin sabiql cf14_measurements --no-run --message-format=json
# Use the executable returned in the compiler-artifact JSON:
python3 scripts/cf14/stage2.py --binary /absolute/test/binary --output /new/raw/directory
RUSTC_WRAPPER= cargo clean --target-dir /private/tmp/cf14-stage2-target
```

The manifest is written before execution: 3 repetitions, delays 0/50/200 ms,
10/100/1000 catalog tables, CSV sizes 50/1000 rows, success/truncation, 600 seconds,
10 MiB raw, 60 seconds per test process. Budget checks occur between test processes
and the final byte total is checked. CSV calls also have a 20-second harness
deadline; lifecycle receives have a 15-second deadline and fewer than 20 actions
per transition. Harness deadlines fail the run, rather than becoming adapter
latency samples. Failed-run logs are retained. A process-group watchdog covers the
owned harness and fake CLI children. PID existence is checked 500 ms after each
test process ends; this is not a continuous process-lifecycle/concurrency trace.

The binary hash, measurement/fake/runner source hashes, base SHA and platform are
saved. Development profile, a shared ordinary host, Python startup, XML parsing,
option-file I/O and measurement overhead are included. Compilation and test-binary
startup are outside the measured intervals. Delay is one sleep before each
nonempty XML response, **not network RTT**. XML bytes are generated bytes, not
received/network bytes. DB connections, maximum process concurrency, DB cold/warm
and live-terminal display remain unmeasured (`null`). Median and nearest-rank p95
are descriptive: at n=3 p95 is the maximum, not a stable tail estimate.

## CSV boundary

The existing non-default `test-support` API
`export_mysql_csv_to_path_for_test` owns the secure option file and invokes the
real streaming exporter through `export_to_path`. Its destination is inside a
caller-owned `TempDir`; no Downloads/home destination is selected. This API omits
client-side query policy, so this is **not a measurement of the full public export
workflow** (confirmation, policy, effect scheduling and folder opening excluded).

Before extending the fake, the real call sequence was observed in
`stage2-observe-4cf0b6f3/csv-0-10-50-none-0-cli.jsonl`: server probe; autocommit and
read-only SETs; session marker; SELECT. The existing marker XML already supported
this sequence. The fake now responds to that exact fixture SELECT with the
requested row count, or emits rows without the closing resultset and exits with
synthetic ERROR 2013. This tests local CSV failure cleanup, not DB/network failure
or rollback. A fixed integer column permits exact CSV byte-content validation,
including header and all rows; row counts exclude the header. CSV data itself is
temporary, while row/byte/time/error/cleanup observations are committed.

## Connection and drawing boundary

The test reuses the lifecycle cache-test scenario and `src/tests/harness` state,
sized-terminal and render helpers. It drives real `SwitchConnection` Actions:
A → B → A, using two distinct synthetic DSNs (ports 1 and 2) for the same fixture
schema. The cache is populated through normal reducer transitions, never inserted
by the measurement. The shared state helper starts with its default PostgreSQL
identity; A is the first measured MySQL connection and has no cache.

`reduce` produces effects executed by `EffectRunner` with a real `MySqlAdapter`;
the returned and channel-delivered Actions go back through `reduce`. An explicit
effect allowlist prevents unrelated settings/history/clipboard/export I/O. A
120×40 TestBackend is drawn after each action through `render_and_get_buffer_at`,
with an assertion that the target list contains `items`. No table is selected,
so this measures list readiness, not Inspector/preview readiness. All three
transitions must reach a fresh MetadataLoaded and EffectiveUserLoaded. Tracked
tasks are cancelled/joined at the end.

Every time is measured from the initiating SwitchConnection:

| Field | Endpoint |
|---|---|
| `list_state_ms` | target identity has metadata after reduction; may be restored cache |
| `metadata_loaded_ms` | fresh MetadataLoaded has been reduced |
| `first_list_draw_ms` | first target-list TestBackend draw and buffer clone return |
| `refreshed_list_draw_ms` | draw and buffer clone after fresh MetadataLoaded return |
| `elapsed_ms` | EffectiveUserLoaded reduced, drawn and resulting effects executed |

The cached-return list may be drawn after probe completion but before metadata
revalidation. These are explicit test-loop boundaries: the production main-loop
render scheduler, terminal transport and a user's visible pixels are not timed.
Earlier frames and assertion overhead can contribute to later endpoints. Cache
restoration is application-state reuse, **not DB warm-up or live connectivity**.

## Authoritative results

117 observations: 36 CSV (18 success, 18 truncation) and 81 connection transitions
(27 A → B → A sequences). All raw assertions passed; the authoritative directory
contains 398,412 bytes. Source hashes match the committed measurement inputs.
Every sampled process had no residual PID at the 500-ms check. All 36 CSV calls
left zero `.part` files; all 18 failures left no final CSV. Successes contained
exactly 50 rows/143 bytes or 1000 rows/3893 bytes, including the CSV header in bytes.
The fixture observed 2 fake processes/5 SQL statements per CSV call and 4 fake
processes/11 SQL statements per connection transition. These are not DB connection
counts; SETs count as SQL statements even though they generate no XML response.

At **100 tables**, medians in milliseconds (n=3 per row):

| Delay per XML | Transition | List state | Fresh metadata | First list draw | Refreshed list draw | Effective-user endpoint |
|---:|---|---:|---:|---:|---:|---:|
| 0 | first connection | 257.9 | 257.9 | 260.3 | 260.3 | 423.8 |
| 0 | cached return | 106.5 | 257.9 | 107.9 | 260.2 | 419.6 |
| 50 | first connection | 505.1 | 505.1 | 512.9 | 512.9 | 875.0 |
| 50 | cached return | 168.1 | 513.0 | 169.9 | 516.0 | 872.9 |
| 200 | first connection | 1148.3 | 1148.3 | 1154.4 | 1154.4 | 1954.0 |
| 200 | cached return | 338.9 | 1144.1 | 341.7 | 1150.1 | 1968.5 |

The cache allows an earlier list frame after the probe but does not remove the
metadata/effective-user CLI work. The measured effective-user endpoint remains
similar for first connection and cached return. This establishes a distinction
between list availability and revalidation, not a speedup from a production code
change. No real-DB cold/warm conclusion follows.

For **1000-row CSV**, success medians are 199.0/404.0/889.0 ms and truncation
medians 106.9/300.7/798.4 ms at 0/50/200 ms synthetic delay. A failed stream has a
different termination path; its shorter duration is not a successful-export
optimization. Summary JSON retains per-condition n, median, nearest-rank p95,
minimum and maximum, including all table sizes and the other-connection phase.

Focused ignored tests, targeted root-bin/tests Clippy with `-D warnings`,
`cargo fmt --all -- --check`, custom lints and raw invariant checks passed. Full
workspace checks are delegated to the PR's exact-head CI. Real DB timing,
connection counts/RTT, DB cold/warm, live TUI/Inspector/preview rendering, and
measurement-backed production optimization or a retain-current-design decision
remain outside this stage.
